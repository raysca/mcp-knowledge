Private retrieval for local RAG

Your documents, searchable over MCP and REST.

Run a private retrieval layer on hardware you control. MCP Knowledge parses common document formats, embeds them locally, and returns explainable hybrid results to MCP clients or your own applications. Your client decides how to generate the answer.

Explainable by default

Not a black box.

Most retrieval systems hand back a paragraph and a shrug. Every hit here carries its full provenance: which method found it, where it placed on each side, and the fused score that decided the final order.

  • Reciprocal Rank Fusion, k=60 Vector and lexical candidates merged by a formula you can recompute by hand — no opaque reranking model in the middle.
  • Traceable source location Chunks point back to a heading, page, or section of the original file, not just a filename.
  • No stemming surprises Lexical search matches SKUs, error codes, and part numbers literally instead of quietly stemming them away.
  • A playground to prove it The bundled dashboard runs hybrid, vector, and lexical side by side on your own documents.

How it works

From file to retrieval, entirely on your machine.

Nothing in this path calls a hosted model, and the costly parsing and embedding stages are isolated from the process serving requests.

01

Ingest

Upload via the dashboard or REST, point at a URL, or watch a folder. A .zip is unpacked and every allowlisted file inside gets indexed.

02

Parse in a subprocess

AnyDoc handles PDF, Word, PowerPoint, Excel, HTML, and Markdown in a spawned process — a hostile upload crashes it, not the server.

03

Embed in a worker

Chunks are embedded locally by a vendored MiniLM model on a worker thread, so a bulk import never stalls in-flight searches.

04

Store & fuse

One libSQL file holds vectors and the FTS5 index. Both sides run in parallel per query and fuse into a single ranked list.

What you get

Infrastructure, not another chat window.

MCP-native

A Streamable HTTP MCP endpoint sits beside the REST API on the same origin and port. Point Claude, Cursor, or any MCP client straight at it.

No hosted model API key

Embeddings run locally on a vendored MiniLM model. No OpenAI, Anthropic, or Cohere account is needed to ingest or search a single document.

One process, one container

Bun.serve() serves dashboard, REST, and MCP together. libSQL and the local filesystem hold the rest — no external database to run.

Isolated by design

Parsing is a spawned subprocess, embedding is a worker thread. Malformed or hostile input can't take the serving process down with it.

Rebuildable by design

Originals are canonical. Chunks, embeddings, and indexes can all be regenerated from them, and backup/restore is documented rather than assumed.

Multi-arch and gated

Published for linux/amd64 and linux/arm64, smoke-tested offline on both architectures before any tag is pushed.

A focused retrieval layer

Choose it when control matters more than orchestration.

MCP Knowledge is intentionally smaller than an agent framework and more complete than a retrieval library.

Good fit

  • Your documents need to remain on hardware you control
  • MCP clients and REST applications need the same corpus
  • You want to inspect why each result was ranked
  • You want one container rather than a retrieval stack to assemble

Use something else if

  • You need a chatbot or agent framework out of the box
  • You need multi-tenant or distributed deployment in v0.1
  • You need OCR for scanned PDFs
  • You need hosted-scale reranking or answer generation

Quick start

Run the published image.

Docker Engine or Docker Desktop is the only prerequisite — Bun, the parser, and the embedding model all ship inside the image.

Run it

bash
$ docker run -d \
  --name mcp-knowledge \
  --restart unless-stopped \
  -p 127.0.0.1:3000:3000 \
  -v mcp-knowledge-data:/app/data \
  ghcr.io/raysca/mcp-knowledge:main

$ curl --fail http://127.0.0.1:3000/health

Connect an MCP client

mcp.json
{
  "mcpServers": {
    "knowledge": {
      "url": "http://127.0.0.1:3000/mcp"
    }
  }
}
  • Dashboard and playground at http://127.0.0.1:3000; MCP at /mcp, same origin, same port.
  • MCP tools are read-only — search_documents, get_document, get_chunk, list_documents, list_collections. Use REST to write.
  • The loopback-only setup above has no authentication. Set DASHBOARD_PASSPHRASE and generate an API key before exposing it to a LAN, proxy, or tunnel.
  • Everything persists in the mcp-knowledge-data named Docker volume. Removing the container does not remove its data.
  • The main tag tracks the current published build. Pin a versioned tag when the first release is published.
