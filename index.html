Explainable by default

Every answer comes with a citation slip.

Most retrieval systems hand you a paragraph and a shrug. This one treats every hit like a library index card: where it came from, why it ranked where it did, and which retrieval method actually found it — vector similarity, lexical full‑text, or both.

How it works

From file to answer, entirely on your machine.

Drop in a file

Upload through the dashboard, REST API, a watched folder, or a URL. PDFs, Office docs, HTML, Markdown, and more — even a .zip of files.

Parse, chunk, embed

A subprocess parses the document; a worker thread embeds it locally with MiniLM. A bad file can't take the server down.

Search hybrid

Vector similarity and lexical full-text run in parallel and fuse into one ranked list — fast enough for a live playground.

Cite the source

Every result over REST or MCP carries its rank breakdown and original location back to the caller.

What you get

Infrastructure, not another chat window.

MCP-native

A Streamable HTTP MCP endpoint sits next to the REST API on the same origin — point Claude, Cursor, or any MCP client at it directly.

Zero required AI vendor

Embeddings run locally via a vendored MiniLM model. No OpenAI, Anthropic, or Cohere key required to ingest or search a single document.

One container, one process

Bun.serve() handles the dashboard, REST, and MCP together. libSQL and the local filesystem hold everything — no external database to run.

Isolated by design

Parsing runs in a spawned subprocess; embedding runs in a worker thread. A hostile or malformed upload can't crash the serving process.

Real recovery story

Originals are canonical — every chunk and embedding can be rebuilt from them. Documented offline backup and restore, not a promise.

Multi-arch, tagged, tested

Published for linux/amd64 and linux/arm64, smoke-tested offline after build on both, before any tag is pushed.

Quick start

Running in about a minute.

# prerequisite: Docker Engine or Docker Desktop, nothing else docker compose up -d # upload a document curl -sS -X POST http://127.0.0.1:3000/api/v1/documents \ -F "file=@handbook.pdf" # ask a question curl -sS -X POST http://127.0.0.1:3000/api/v1/search \ -H 'content-type: application/json' \ -d '{"query":"refund policy","mode":"hybrid"}'

No DASHBOARD_PASSPHRASE set means loopback-only, no-auth — fine for a machine only you can reach. Set one before exposing it any further.

  • Dashboard and playground at http://127.0.0.1:3000
  • MCP endpoint at /mcp, same origin, same port
  • Point INGEST_DATA_DIR at a folder to watch it continuously
  • Everything persists in one named Docker volume

Honest scope

What this deliberately isn't.

This is

  • A document store with explainable hybrid search
  • An MCP server for retrieval, plus a REST API and dashboard
  • Self-hosted infrastructure with no external AI requirement
  • Single-tenant, local-first, one container to operate

This is not

  • A chat app or an agent framework
  • Multi-tenant or built for distributed deployment (v0.1)
  • A hosted OCR pipeline — scanned PDFs need OCR first
  • A reranking or LLM-answer-generation layer
