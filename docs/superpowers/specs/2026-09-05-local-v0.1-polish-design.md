# Local v0.1 Release Polish Design

**Date:** 2026-09-05

## Purpose

Prepare the existing local Document Knowledge MCP service for a dependable public
`v0.1` release. A new user should be able to start it through Docker, ingest and
search a corpus of roughly 100 to 1,000 documents, connect an MCP client, and
protect, back up, and recover their data without understanding the implementation.

This is a release-polish effort. It preserves the existing local architecture and
does not expand the product into a distributed or hosted service.

## Release outcome

The release is accepted when:

- Native `linux/amd64` and `linux/arm64` images are published under one
  multi-architecture image reference.
- A documented Docker Compose command starts the service with one persistent data
  volume.
- The container exposes a working health check and stops gracefully.
- Markdown, plain text, HTML, PDF, and DOCX ingestion pass on both architectures.
- Retrieval quality is measured against a representative mixed-format evaluation
  corpus rather than only the existing ten-document regression corpus.
- Backup, restore, restart, reindex, and interrupted-ingestion recovery are tested.
- Expected user-facing failures explain the cause and a useful next action.
- Performance and resource use are recorded at approximately 100, 500, and 1,000
  documents so the release documentation can set realistic expectations.
- The application performs embedding inference without outbound network access
  after the image has been built.

## Existing architecture

No new service layer, storage abstraction, or deployment profile is required. The
existing data flow remains:

```text
Docker volume -> canonical original -> parser subprocess -> normalized blocks
              -> chunks -> embedding worker -> libSQL vector and FTS indexes
              -> REST API, MCP, and dashboard
```

Original documents remain canonical. Normalized documents, chunks, embeddings,
and indexes remain rebuildable derived data. Parsing continues in a subprocess,
and embedding continues in a worker thread so ingestion cannot block or crash the
HTTP server process.

## Workstreams

### 1. Baseline hygiene

Before adding release artifacts, restore a clean engineering baseline:

- Fix the existing strict TypeScript check failure in the worker-loop unit test.
- Add an explicit repository type-check command and keep it green with the test
  suite.
- Replace stale repository guidance that still describes the project as
  planning-only.
- State the supported formats, local-only scope, and release constraints in one
  authoritative place.

This workstream does not include unrelated refactoring.

### 2. Docker release

The supported installation path is Docker. Release packaging includes:

- A reproducible multi-stage image with pinned Bun and dependency inputs.
- Native builds for `linux/amd64` and `linux/arm64` using Docker Buildx.
- One minimal Compose service with an explicitly named persistent data volume.
- A container health check against the local HTTP health endpoint.
- Graceful handling of container termination.
- A build-and-smoke workflow that validates both architectures, including PDF and
  DOCX parsing because native parser dependencies are the main portability risk.
- A multi-architecture manifest published only after both platform checks pass.

The Compose definition does not include PostgreSQL, MinIO, a reverse proxy, or a
second worker service.

### 3. Retrieval evaluation

Extend the committed evaluation material with a representative, non-sensitive,
mixed-format corpus and relevance judgments. The evaluation covers:

- Exact identifiers, codes, and product names that favor lexical retrieval.
- Paraphrased questions that favor semantic retrieval.
- Similar documents that are easy to confuse.
- Heading and section-level provenance.
- Ambiguous queries.
- Queries for which the corpus has no good result.

The repeatable evaluation reports at least Recall@5, mean reciprocal rank, and
search latency. Existing retrieval constants and algorithms are changed only when
a committed evaluation case demonstrates a meaningful failure. A tuning change
must preserve exact-identifier retrieval and cannot merely improve one hand-picked
query.

The release records the evaluation corpus size and limitations. It does not claim
general retrieval quality from a small benchmark.

### 4. Data safety and recovery

The single persistent volume contains the local database and canonical document
storage. Documentation and automated checks cover:

- Creating a consistent backup while the service is stopped.
- Restoring that backup into a fresh service instance.
- Restarting with the same volume without duplicate ingestion or lost jobs.
- Recovering from an interrupted ingestion job.
- Retrying a failed job.
- Reindexing a ready or failed document from its canonical original.
- Confirming that restored documents remain downloadable and searchable.

For `v0.1`, an offline, stopped-container backup is sufficient. Online snapshots,
incremental backups, remote replication, and scheduled backup orchestration are
not required.

### 5. Onboarding and diagnostics UX

The Docker-first quick start should take a user from no local state to a successful
search and MCP connection. It explains:

- How to start and stop the service.
- Where persistent data lives and how to remove it intentionally.
- How to enable the dashboard passphrase before exposing the port beyond the local
  machine.
- Supported formats and current OCR limitations.
- How directory ingestion behaves.
- How to connect an MCP client.
- How to inspect, retry, reindex, back up, and restore.

Expected failures exposed through the dashboard and API include a stable error
code, a plain-language cause, and a useful next action. Normal responses and logs
must not expose credentials, internal absolute paths, document contents,
embeddings, authorization headers, or stack traces.

The UX work reuses existing pages and components. It does not introduce a setup
wizard, notification system, or redesigned dashboard.

### 6. Scale validation

Run repeatable tests at approximately 100, 500, and 1,000 representative
documents. Record:

- Total and per-document ingestion time.
- Peak memory use.
- Database and document-volume growth.
- Cold and warm search latency.
- Restart time and time until the service can answer health and search requests.

The purpose is to publish honest operating expectations and identify severe
regressions. There is no speculative optimization target. Performance work is
accepted only when a measured result at the supported scale is clearly unsuitable
for normal local use.

## Implementation sequence

Work proceeds in dependency order:

1. Restore the baseline: tests, strict type checking, and current documentation.
2. Make the Docker image and Compose startup reproducible on the host architecture.
3. Add cross-architecture build and smoke verification.
4. Expand retrieval evaluation and establish a recorded baseline.
5. Verify backup, restore, restart, reindex, retry, and interruption recovery.
6. Polish onboarding, failure explanations, and troubleshooting around verified
   behavior.
7. Run the 100/500/1,000-document scale checks and document results.
8. Run the complete release matrix, publish the multi-architecture image, and tag
   `v0.1.0`.

Retrieval tuning follows evaluation, and performance optimization follows scale
measurement. Documentation is finalized after the workflows it describes have
been exercised.

## Verification matrix

The release matrix covers:

- Clean image build and first start with database migration.
- Restart with a persistent volume.
- Markdown, text, HTML, PDF, and DOCX ingestion.
- Corrupt, unsupported, oversized, OCR-required, and timed-out inputs.
- Duplicate, retry, delete, purge, and reindex behavior.
- Hybrid search provenance and explain output.
- MCP initialization, tool listing, and document search through a real SDK client.
- Backup followed by restore into a fresh container and volume.
- Native PDF and DOCX parsing on both `linux/amd64` and `linux/arm64`.
- Embedding and search with outbound network access disabled after build.

Existing unit, integration, crash-isolation, and retrieval tests remain required.
A release is blocked by a test or type-check failure, architecture incompatibility,
data-loss or recovery failure, non-functional documented workflow, or severe
usability defect in the primary Docker path.

Minor feature requests and speculative performance improvements do not block the
release.

## Explicit exclusions

YAGNI exclusions for `v0.1` are:

- PostgreSQL, pgvector, and S3.
- Multiple API or worker replicas and distributed job locking.
- Kubernetes or production cloud deployment templates.
- Multi-tenancy, workspaces, and complex authorization scopes.
- Webhooks and notification delivery.
- Hosted embedding providers and alternative embedding models.
- Rerankers, chat interfaces, and agent behavior.
- Continuous filesystem watching.
- New OCR infrastructure.
- A large metrics or observability stack.
- Online, incremental, remote, or scheduled backups.

These items may be reconsidered only in response to demonstrated user demand or a
measured limitation of the local product.

## Release artifact set

The final `v0.1` artifact set consists of:

- A multi-architecture container image and manifest.
- A minimal Compose file.
- Docker-first quick-start, security, backup/restore, troubleshooting, supported
  formats, and performance guidance.
- Automated tests and smoke workflows for both target architectures.
- Retrieval evaluation fixtures, relevance judgments, and recorded results.
- Repeatable local scale-test tooling and recorded results.
- Release notes describing capabilities, limitations, and upgrade expectations.
- Git tag `v0.1.0`.
